# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build rules

- **Always build and run the release profile. Never build a debug build.** Run a release build to validate changes before handing them off. Every cargo invocation in this repo, in docs and in CI carries `--release` (or `-r`): `cargo build --release`, `cargo run --release`, `cargo test --release`, `cargo check --release`, `cargo llvm-cov --release`. GPUI debug builds are slow to compile, slow to start and render at a fraction of release frame rates. Do not add `[profile.dev]` tuning as a workaround; use release.
- **Installers are built with the `dist` profile**, which inherits `release` and adds LTO, `codegen-units = 1` and symbol stripping: `cargo packager --profile dist`, `cargo generate-rpm --profile dist`. `dist` is a release build with slower, tighter optimisation; it is used for packaging only, never for the edit-test loop.

## Common commands

```bash
cargo run --release -p BatchMkvExtract                   # run the app
cargo check --release --workspace                        # fast Rust type-check without linking
cargo test --release --workspace                         # run the whole test suite
cargo llvm-cov --release -p bme-core --summary-only --fail-under-lines 90   # the CI coverage gate
cargo build --profile dist -p BatchMkvExtract            # installer build: release + thin LTO
cargo packager --profile dist -p BatchMkvExtract -f app,dmg   # or nsis,wix / deb,appimage (cargo-packager 0.11.8)
cargo generate-rpm --profile dist -p crates/bme-app      # .rpm on Linux (cargo-generate-rpm 0.21.1)
```

To try the app by hand without touching your own settings, start it with a scratch home: `HOME=/tmp/bme-home cargo run --release -p BatchMkvExtract` (on macOS and Linux the config directory follows `$HOME`; on Linux only while `XDG_CONFIG_HOME` is unset).

Version bumps are done with a Deno script — edit the two arguments at the bottom of `scripts/ts/change-version.ts` and run:

```bash
cd scripts/ts && deno task change-version
```

That rewrites `crates/bme-app/Cargo.toml`, `crates/bme-core/Cargo.toml`, `crates/bme-platform/Cargo.toml`, all three `.github/workflows/*.yml` files and the `CFBundleVersion` of `crates/bme-app/packaging/macos/Info.plist`. It then runs `cargo update -w` (so `Cargo.lock` records the new workspace versions) and warns when `docs/release_notes.md` has no `## <version>` section yet. Before a release, run the manual checklist in `docs/development.md` ("Release checklist") on the `dist` installers from CI.

Versions up to 0.3.0 were a different implementation; its source is in the git history (tag `0.3.0`). Every 1.0.0 installer upgrades a 0.3.0 install in place, and a config written by 0.3.0 loads unchanged. Code comments that compare with "0.3.0" describe that version's behaviour.

### Rust toolchain

The toolchain is pinned in `rust-toolchain.toml` at the repository root (currently **1.100.0**); gpui-kit needs 1.92 or newer. `.rustfmt.toml` sits at the root too (`max_width` 120, `tab_spaces` 2). The GitHub Actions workflows use `actions-rust-lang/setup-rust-toolchain` (v2) **without** a `toolchain:` input, so the action installs the pinned toolchain; with `toolchain: stable` it would also run `rustup override set stable` on the repository root, and that directory override outranks the toolchain file. They set `build-warnings: warn`: v2 otherwise sets `CARGO_BUILD_WARNINGS=deny`, which would turn every rustc warning into a CI failure, so CI fails on errors and failing checks only.

### Tests

Unit tests are inline (`#[cfg(test)] mod tests {}`, or a `tests.rs` beside a module's `mod.rs`). The golden test `crates/bme-core/tests/extract_args_golden.rs` holds `extract_args` and the drive key to `tests/golden/*.json`: values recorded by running 0.3.0's extraction code unchanged under Deno, plus `commands.json`, the copyable commands written by hand per platform; change them only when the behaviour is meant to change (`format_hms.json` is read by `bme-app`'s `domain::format` test). `cargo test --release --workspace` runs all of them, the app's headless UI tests included. Coverage is measured with `cargo-llvm-cov`: the whole `bme-core` crate is held to ≥ 90 % line coverage, enforced by the Linux CI workflow (`.github/workflows/linux_build.yml`) via `cargo llvm-cov --release -p bme-core --summary-only --fail-under-lines 90`; local baseline is ~94 % (~96 % on Linux). The extract queue is tested through a fake process launcher (`ExtractQueue::new`), `mkvtoolnix` through fake tool scripts (Unix), the update check through a local HTTP stub. How to test the UI is under "GPUI and gpui-kit notes" below.

## Architecture

### Workspace

The Rust code is a Cargo workspace (root `Cargo.toml`, one `Cargo.lock`, one `target/`) with three members:

- `crates/bme-core` — everything UI-free: the config file, the per-drive extract queue and its `ExtractEvent`s (`extract.rs`), `mkvtoolnix` (tool resolution and detection, `mkvmerge -J` track listing, `mkvextract` launch), `extract_args` (the `mkvextract` arguments and output file names), `services` (file intake, output directories, BetterMediaInfo), the update check, and the result types of `protocol.rs`. No GUI toolkit and no async runtime: long-running work runs on plain threads.
- `crates/bme-platform` — per-OS code GPUI lacks: the taskbar / Dock / launcher progress (`ITaskbarList3`, `NSDockTile`, the `com.canonical.Unity.LauncherEntry` D-Bus signal) and the display a window is on (Windows; GPUI's own lags at mixed display scales).
- `crates/bme-app` — the gpui-kit application, package `BatchMkvExtract`: a library `batch_mkvextract` with all code and tests, and a three-line binary that calls `batch_mkvextract::run()` (`#![windows_subsystem = "windows"]` unconditionally, there is no debug build). The app identity lives in `lib.rs` constants: `APP_IDENTIFIER` (`com.caoccao.batch-mkvextract`, also the Windows AppUserModelID), `DESKTOP_ID` (`BatchMkvExtract`, the Linux desktop file basename, Wayland app id and launcher-progress URI).

### Application startup

`lib.rs::run` installs the log (`logging.rs`: `BatchMkvExtract.log` in the config directory, the previous run's kept as `BatchMkvExtract.previous.log`, and a panic hook), reads the config, layers gpui-kit's own strings from the locale files (`i18n::install_component_strings`, before `gpui_kit::init`), sets the app identity, the locale (`i18n.rs`; `t!` through the crate-local `tr!` macro that returns a `SharedString`) and the theme (`theme.rs`); creates the extract-event channel and the channel for the MKVToolNix directory an extraction finds by itself; builds `Services` and `Stores`; starts the extract-event bridge; binds the shortcuts and the global action handlers (`ui/actions.rs`, so they work without focus); installs the macOS menus; opens the main window (`platform/window.rs`); installs the Quit handler behind the close guard; reports an unreadable config file; takes the launch arguments; watches BetterMediaInfo; and starts the update check. The app quits when the main window closes, even with the topmost window open.

### State (`state/`)

Every view gets the stores as `Stores` (`config`, `files`, `queue`, `ui`, plus the extract backend, the taskbar and the tool detector). `Stores::new` takes `Services` — config `Persistence`, a `TrackSource` for `mkvmerge -J`, an `ExtractBackend` for enqueue, cancel and shutdown, the `Taskbar`, the `ToolDetector` — so tests pass fixtures and recorders.

- `ConfigStore` (`state/config.rs`): optimistic edits, background writes with a revision so an older write never lands last, a synchronous flush on quit; only a write that succeeded counts as written, so after a failure the next edit or the quit writes again, and the first failure after a success is emitted as `ConfigEvent::SaveFailed` (a toast, `notifications.rs`); the profile edits `add_profile`, `delete_active_profile`, `set_active_profile`, `reset_active_profile`, `update_active_profile` (a new profile is `ConfigProfile::named`). Each profile operation emits `ConfigEvent::GroupMode` with the profile's `defaultGroupMode` (`update_active_profile` only when it changes that field), which sets Group Mode even over a session toggle. Every config write of the app goes through it: settings, window geometry, the update check's `lastChecked` / `lastVersion` (`update::record_check`), tool paths, and the MKVToolNix directory an extraction auto-detects. The core never writes the config file.
- `FileStore` (`state/files/`): the files, deduplicated by `file_identity` (the path as the file system resolves it), their tracks and track counts, selections, output directories (per file, and the session's global one), Group Mode and whether BetterMediaInfo is available; it derives the file list's entries after every change. `load.rs` lists every file once through the `TrackSource` on the background executor, at most four at a time (`MAX_CONCURRENT_LOADS`); each listing runs with the MKVToolNix directory of the settings, has a generation of its own and a cancel flag: removing the file or changing the MKVToolNix directory cancels it (its `mkvmerge` is stopped), frees its place at once and drops its late result, and `mkvtoolnix::list_tracks` stops `mkvmerge` after `LIST_TRACKS_TIMEOUT` (60 s, `TrackListError::TimedOut`). A failure is kept as a `TrackListError` until the file is removed, its table's Retry is pressed (`FileStore::retry_load`) or the MKVToolNix directory changes, which lists every failed file again. When a file's tracks arrive and it has no selection yet, the active profile's `TrackSelector` picks them; an existing selection, also an empty one, is never replaced. The files of a group card share one selection: the first member's, else the profile's over the first member's tracks. They share a card only when their tracks line up (`domain::grouping::grouping_key`: the directory, the counts, and every row's key with the language and codec id of a video, audio or subtitle track), so a key names the same track in every member. `table.rs` holds `TableScope` (one file, or a group card's files, whose checkbox writes go to every member).
- `QueueStore` (`state/queue.rs`): driven by `ExtractEvent`s; ticks every second while an extraction runs. It tracks a batch from the moment an item waits or extracts until none does and emits `QueueEvent::Drained(QueueBatch)` once; `QueueSummary` gives the done and total counts and the overall percent. It also holds the reservations of extractions being prepared (a token each) and the outputs each handed-over extraction writes until it finishes (`output_owner`). The summary, `has_active`, the ticker and the batch read running totals that every item change keeps (`Totals`, through `QueueStore::edit`), so a progress event or a tick scans nothing; in tests every change asserts that the totals equal a full recount.
- `UiState` (`state/ui.rs`): the tabs, toasts (`show_toast`, `show_snackbar`), the toolbar's Quit when complete, System Notification and Topmost Notification toggles (session-only), the open toolbar menu (`ToolbarMenu::{Profile, Overflow}`), the version the update banner announces, and the closing flag (`set_closing`).

A store notifies only on structural changes (files or queue items added or removed, a status, the groups, the first or last selection); every change is also emitted as `FileEvent::Changed` / `QueueEvent::ItemChanged` naming the files, for per-card and per-row repaints.

### Event flow

- **Extractions**: `extract_events.rs` installs the core's sink (`extract::init`). The worker threads push `ExtractEvent`s into an `async-channel`; one foreground task applies them to `QueueStore` in the order they were sent. Nothing polls.
- **Enqueue and the other actions that span stores** (`actions.rs` at the crate root): an `ExtractRequest` is read on the foreground (the file, its selected tracks, the active profile, and the output directory: the file's own, else the session's global one, else the file's folder), and each file that is not waiting or extracting is listed as waiting at once (`QueueStore::reserve`, so Cancel, Delete and Cancel All see it and end it at once); on the background executor the output directory is created (`services::ensure_output_path`; a failure toasts `notification.failedCreateOutput` and queues nothing) and the arguments and the files it writes are built (`extract_args::build_extract_plan`, a VobSub `.idx` included); then each file whose reservation still stands is handed to the extract queue, in request order. A file is refused with a toast when two of its rows would write one file, when an output is a listed source file, or when another waiting or extracting file writes one of its outputs (compared by `extract_args::output_key` inside the output directory as the file system resolves it; the first file asked for keeps it until it finishes). A file that is there already is replaced, as `mkvextract` does. Extract All walks the files in on-screen order (`FileStore::files_on_screen`), a group card's files where the group is, so a drive's queue order matches the file list. Also cancel, Cancel All, Resume and Resume All (cancelled and failed files again, with their current selection and the active profile), Clear Completed, Clear (the file list and the queue, only while nothing is active), Delete (a waiting file is cancelled first; an extracting one is not removed), a group card's Clear All, Copy Command and Copy All Commands, Open in BetterMediaInfo and its detection.
- **Notifications** (`notifications.rs`): every finished file gets a top-centre toast (`Completed in HH:MM:SS`, the warnings, or the localised error); a drained batch becomes a `CompletionNotice`. **The OS notification and the topmost window are sent once per drained batch, not per file**, only when an extraction of the batch completed or failed, and never while the window closes (`UiState::set_closing`, set by the exit dialog's Yes). A batch of one completed file names the file with "Completed in"; any other shows the counts and "Finished in" from the first start to the last end. The root view delivers it: `Notification::…system()` (the OS notification centre only; an unbundled `cargo run` on macOS drops it silently), the topmost window, and with Quit when complete on, the quit after the last job.
- **Taskbar progress**: `platform::taskbar::Taskbar` (a service: `bme_platform::TaskbarProgress` in the app, a recorder in tests) is set from `QueueSummary` on every queue change while an extraction is active and hidden otherwise.
- **Update check**: `updates.rs` runs `bme_core::update::startup_check` (an `UpdateSource` that is GitHub's `/releases/latest` in the app) on the background executor and records the check through the config store, so a later settings edit never writes an older `update` block; `ui/update_banner.rs` shows a newer version above the toolbar with Skip this version.
- **External tools**: `tools.rs` is the `ToolDetector` service behind the Integration settings and the BetterMediaInfo watch (core `mkvtoolnix::detect_mkvtoolnix` and `services::detect_better_media_info`; a stand-in in tests) and the relay of the MKVToolNix directory an extraction finds by itself (`mkvtoolnix::init_auto_detected` → `tools::store_auto_detected` → `ConfigStore`; an `AutoDetected` carries the configured path it was found from and is dropped when the settings hold another path by then).

### Views (`ui/`)

- `root.rs` is the window content: update banner, toolbar, tabs and status bar, plus what belongs to the whole window (OS file drop, toasts, geometry persistence, the title `BatchMkvExtract v{ver}` with ` - done/total` while extracting, the taskbar progress, the completion notice, live language and theme changes, the close request). `toolbar.rs` has the icon buttons with tooltips (Set global output path · Extract All (labelled) · Resume All · Cancel All · Clear Completed · Clear · Quit when complete · System Notification · Topmost Notification · Group Mode · Profile · Settings · About), an overflow menu behind a chevron when the window is narrow, the Group Mode toggle (highlighted while on) and the Profile menu: gpui-kit `PopupMenu`s in a controlled `Popover` whose open state is `UiState::open_menu`, so F9 opens it too. `main_content.rs` has the tabs (File List, Queue, and the closable About tab); the tab body has a 1 px padding and each card a 1 px margin (`ui::TAB_PADDING`, `ui::CARD_MARGIN`). `welcome.rs` (four app cards: this app, BatchMkvMerge, BetterMediaInfo, BDMaster), `about.rs` and `status_bar.rs` complete the shell.
- **File list** (`file_list.rs`) and **cards** (`cards/`): `FileCard` (status icon, the path, the summary with the track counts and `To path …` for its own folder, Set Output Path, Open in BetterMediaInfo, Copy Command, Extract, Delete, the waiting tint, the progress row with `elapsed / ETA` and Cancel while active, the track table) and `GroupCard` (the directory and summary, Set Output Path for every file, Open in BetterMediaInfo with every file, Copy All Commands, Extract All, Clear All, the files with status and progress on the left of a 6 px splitter, 240 px wide, min 160 px, at least 240 px left for the table; on the right the first file's table, whose selection applies to every file). The file list keeps cards by their file or group key, so a card keeps its state while files come and go around it. Card messages are bottom-centre toasts (`UiState::show_snackbar`).
- **Track table** (`track_table.rs`): read-only, built on gpui-base's interactive `Table` primitives, because gpui-kit's composable `Table` rows take no mouse handlers. Columns: the checkbox, ID, Number, Type (emoji with the type as tooltip), Codec, Track Name, Language; a click on a row toggles its checkbox; select-all uses `Checkbox::indeterminate`; a track whose codec `mkvextract` refuses (`extract_args::is_extractable`: the codecs its manual lists, plus AV1, checked against v101.0) has a disabled checkbox with the reason as its tooltip and label, and is never selected by the profile, select-all or a request, because one such track makes `mkvextract` refuse the whole extraction; a spinner while a file of the card loads, the listing's error with Retry, `No tracks found.`; disabled while a file of its card waits or is extracted.
- **Output path dialog** (`output_dialog.rs`, `OutputPathDialog`): directory mode for a card, a group card and the toolbar's global output path; a hint line, a 300 ms debounced "will be created" warning, a writable check on OK; an empty field clears the folder.
- **Queue** (`queue/`): one table per drive key, titled with the drive except the single `default` one. `QueueRow` entities draw as cached views at their measured height so only the extracting row repaints. A row's path is the read-only, one-line text a file card shows its path with (`ui/selectable_path.rs`: a gpui-base `Textarea` with Copy and Select All in its context menu), so it can be selected and copied. Waiting and extracting rows offer Cancel; failed and cancelled rows offer Resume. The status (`Extracting N%`, coloured by status) has the error or the warnings as its tooltip, and the table scrolls sideways when the File Path column would fall below 200 px. Resume All, Cancel All and Clear Completed in the toolbar cover all drives.
- **Topmost window** (`topmost.rs`, `TopmostWindow`): a 440×200 `PopUp` window centred on the main window's display work area, reused while open; Escape, Enter and Close close it; with Quit when complete on it offers Quit and `OK, but do not quit`. On Wayland it is an overlay layer-shell surface, falling back to `PopUp` without layer-shell.
- **Settings** (`settings/`): gpui-kit's `setting::Settings` component in an 880 px modal (90 % of the window's height, narrower in a small window) with outlined groups and four pages (Appearance, Integration, Profiles, Update) and their groups listed under each page in the sidebar; gpui-kit's per-page Reset All goes back to `Config::default()` on every page but Profiles. Every control writes its config field at once (tests compare the serialised config). Open the dialog from the toolbar, Ctrl+Comma (Cmd+Comma on macOS), F10 or the macOS app menu. Appearance: the mode, the 4 × 5 theme swatches, the language by its own name. Integration: one `ToolPathRow` (`integration.rs`) drives Browse / Detect for both tools; it checks the text 250 ms after the last edit at that path only (`tools::Lookup::Path`: what it finds there instead, the folder of an executable or a versioned macOS bundle, replaces the text), stores it on blur, and Detect also looks for a running application and in the usual install places (`Lookup::Running`), the only lookup that may put in a tool found elsewhere. The cards' Open in BetterMediaInfo follows `Lookup::Installed` (the path, then the usual install places). Profiles (`profiles.rs`, `ProfileEditor`): the active profile, a new name with Add, Delete and Reset (both ask first; Enter and Escape answer No), Default group mode, Track Selection (an auto-select checkbox per track type, a language filter for video, audio and subtitles) and File Name Templates (a template per track type, the placeholders hint below them). Every field edits the active profile as it is typed; a profile switch or Reset fills in each field whose value changed. Update: the check interval. A row of a text field and buttons wraps the buttons below the field under `ui::settings::FIELD_MIN_WIDTH`.
- **Numeric word navigation** (`ui/word_navigation.rs`): one app-wide keystroke interceptor (installed by `ui::actions::install`). It looks the key up with `cx.key_bindings().borrow().bindings_for_input(...)`, because an interceptor gets `action: None`, and acts only when the winning binding is one of gpui-kit's word actions (`MoveToPreviousWord` / `MoveToNextWord`, `SelectToPreviousWordStart` / `SelectToNextWordEnd`, `DeleteToPreviousWordStart` / `DeleteToNextWordEnd`) and the focused input (`WindowExt::focused_input`: every `Input` and `Textarea`, gpui-kit's own and those in dialogs) is not masked or composing. Element action handlers cannot do it: the input's own handler stops propagation, and dialogs are not under the root view. The stops come from `domain::word_navigation::word_command`, one rule on every OS fitted to gpui-kit's jumps: each part of a number is a word, forward jumps end at a part's end, backward jumps at its start, and the separator has no stop of its own. A path field (the output path dialog, the Integration tool paths, the profile's file name templates) sits in an element with the key context `PATH_CONTEXT`, and there a `.` between two letters or digits is such a separator too (`Separators::Paths`), so a file's name and extension are words. Other text without digits is untouched. A word deletion selects its range and lets gpui-kit's own deletion remove it, so undo brings the part back selected.

### Platform (`platform/`)

Window geometry and title (`window.rs`), the close guard (`close_guard.rs`), the macOS menus (`menus.rs`), the file dialogs (`dialogs.rs`: Add Files and Add Folder through `services::get_mkv_files`), the taskbar progress (`taskbar.rs`), and the launch arguments, the files the OS opens as URLs (`ingest_open_urls`: macOS hands "Open With" and Dock drops to `Application::on_open_urls`, registered in `lib.rs::run` before the event loop and relayed through a channel; `services::path_from_file_url` decodes them; `packaging/macos/Info.plist` declares `.mkv` files and folders as documents the app views) and the Quit handler (`mod.rs`).

- Window geometry: GPUI's macOS window opens with a *content* size but reports its *frame* (title bar included), so the saved size is `window.viewport_size()`; a maximized or fullscreen window is not saved, so its restore geometry survives. Saves are debounced 500 ms and repeated on close and Quit. The geometry is saved with the display's UUID (`config.window.display`), as positions alone cannot tell displays apart (mixed scales on Windows, every display at the origin on macOS). The window reopens on that display when it holds the window's centre or origin, else on the display under them, with its centre moved onto the display (GPUI's Windows backend drops bounds whose centre is off it); the default size is 1200 × 900 and the smallest 600 × 450. A saved size that does not fit the visible area of the display the window opens on (a larger display that is gone) is fitted to it, not below the minimum, with the title bar inside (`fit_to_area`); a window that fits keeps its place, also straddling two displays. The bounds are set before the window appears, so it never flashes at a default geometry.
- Close guard: closing the main window, or Quit (Cmd+Q and the application menu on macOS), while an extraction waits or runs asks first. Ctrl+Q is not Quit: it is the file list's Clear shortcut (shown in the toolbar tooltip), which does nothing while an extraction is active. The exit dialog has its own footer so Enter and Escape answer No (gpui-kit dialogs bind Enter to their OK button); Yes cancels the extractions in one request (`extract::cancel_many`) and waits on the background executor up to 3 s for them to end (`ExtractBackend::shutdown` → `extract::shutdown`, so no `mkvextract` outlives the app), then quits. While it waits, no extraction is queued and another close request is left to the wait. When one did not stop, a second dialog offers Wait (Enter and Escape; the window stays) or Quit anyway. A cancel whose kill fails (`extract::KillFailed`) withdraws the request, so Cancel can be pressed again, and says so in a toast.
- File dialogs on Linux go through the XDG desktop portal (`ashpd`), which desktops provide.

### Domain logic

`bme-core` has `extract_args` (below) and `protocol` (`MkvTrack` with `key()` = `"{type}:{id}"`, `TrackCounts`, `TrackListError`, the tool statuses); `bme-app::domain` has `status` (queue item states from `ExtractEvent`s, elapsed and ETA), `grouping` (Group Mode's key and the file list's entries), `format` (`HH:MM:SS`, clock times, the track-type emoji and the count line), `extract_error` and `track_error` (the localised messages of a failed extraction and a failed track listing) and `word_navigation`. Numbers, strings and rounding follow Rust: byte-wise string order and length, `char::is_whitespace`. Word navigation works on UTF-8 byte offsets.

### Themes

`theme::THEMES` holds the twenty config themes with their main colours; each `themes/<name>.json` (light and dark) is derived from it by fixed rules (ring and link = the main colour; dark-mode link hover = the main colour lightened by 20 %; a primary button's text white or 87 % black by the WCAG contrast ratio 3, as in 0.3.0, and its colours fitted so the text reaches 4.5:1 in every state: under white text the main colour darkened as far as needed, hover and active that × 0.7; under dark text the main colour, hover and active it lightened by 30 %), `every_theme_file_is_derived_from_its_main_colour` checks the files (`BME_WRITE_THEMES=1` rewrites them; run the tests again after, as the files are embedded at compile time) and `every_button_label_reaches_the_normal_text_contrast` measures the contrast in the files. Light, dark and auto (following the OS appearance, live) are supported. At narrow widths, buttons wrap below their text field. The queue's fixed columns fit the longest translation on one line.

### File intake and track listing

`bme_core::services::get_mkv_files(paths)` takes dropped, chosen or launch-argument paths as the OS gives them (`PathBuf`s; the launch arguments through `args_os`), each made a full path from the working directory (a folder contributes the `.mkv` files directly inside it, one level, sorted), filtered by `services::is_mkv` (the extension, in any case). A path that does not exist, a folder that cannot be listed and a name that is not valid UTF-8 are returned as `MkvFiles::skipped` instead of failing the whole drop; the app names them in a snackbar. The app lists each file once with `mkvtoolnix::list_tracks` (`mkvmerge -J`, parsed by the pure `parse_identify_json`): the tracks, one `chapters` row when the first chapter edition has entries, and one row per attachment. `mkvmerge` exiting with 1 (warnings) still lists the tracks; a failure carries the reasons `mkvmerge` puts in its JSON `errors`, else its stderr. `domain::track_error` words each `TrackListError` (`NotAvailable | Failed | Parse | Other`) when it is shown.

### Per-drive extract queue

`crates/bme-core/src/extract.rs` owns all live extraction state in an `ExtractQueue` with an injectable `ExtractLauncher`. One process-wide instance sits behind the free functions `init` / `enqueue` / `cancel` / `shutdown`; tests build their own with a fake launcher.

`get_drive_key` returns the Windows path `Prefix` component (`C:`, `\\server\share`) uppercased (`\\?\C:` and `\\?\UNC\…` spellings included), else `"default"`. When a file is enqueued and its drive has no running `mkvextract`, it starts at once on a `std::thread::spawn`'d worker; otherwise it waits in the drive's FIFO. Arguments are a plain `Vec<String>` built at enqueue time, and each file carries the MKVToolNix directory it was queued with (`ExtractQueue::enqueue(file, mkv_toolnix_path, args)`; the app reads it from the settings when the extraction is asked for, the one Copy Command names), so a setting changed while a file waits does not change what it runs. The core never reads the tool paths from its own copy of the config. `cancel_many` cancels several files under one lock, so no waiting one is started by a running one's end, and a worker cancelled before its launch launches nothing; a kill that fails comes back as `KillFailed`. `mkvtoolnix::spawn_mkvextract` passes `--gui-mode` (progress lines `#GUI#progress N%`, independent of MKVToolNix's interface language) and reads stdout and stderr through one pipe. The queue never creates, checks or removes an output: the app creates the output directory before it enqueues, and `mkvextract` replaces a file that is there and leaves what it wrote when it is stopped or fails. Exit code 0 completes, 1 completes with the warnings (`mkvextract` documents it as "at least one warning, but extraction did continue"), anything else fails with `mkvextract`'s error lines. An extraction ends `Cancelled` only when a cancel's kill ended `mkvextract`, and the exit says which: a kill leaves no exit code on Unix and `KILLED_EXIT_CODE` on Windows, where the queue calls `TerminateProcess` itself because `Child::kill` exits with 1. A cancel that meets `mkvextract` exiting by itself leaves the outcome of that exit.

Workers push `ExtractEvent`s into the sink installed with `extract::init`: `Started`, `Progress` (only when the percentage changes), and `Finished` with `Completed | Cancelled | Failed`, the error and the warnings. Every enqueued file gets exactly one `Finished` — also a file cancelled while still waiting, and a worker that panics (`Failed`). When a worker finishes, the task is dropped and `Finished` sent before the drive starts its next file, so a file enqueued again in answer to `Finished` is a new task. The app's sink (`extract_events.rs`) relays them through a channel to `QueueStore`; nothing polls.

### Profiles and filename templates

Profiles live in the persisted config (one `ConfigProfile` per entry, with a shared `activeProfile` pointer). Each profile carries five templates (video, audio, subtitles, chapters, attachments), five auto-select flags, three language filters (video, audio, subtitles; comma-separated, compared without case, empty matches every language) and `defaultGroupMode`. The `Default` profile auto-selects subtitle tracks and starts in Group Mode (`ConfigProfile::named`).

`extract_args::render_template` expands a template with a **single-pass character scanner** (not regex-based — don't regress this). It supports `{file_name}`, `{track_id}`, `{track_number}`, `{language}`, `{codec_name}`, `{track_name}`. `{{` / `}}` escape to literal braces; unknown placeholders, and a `{` that is never closed, are emitted verbatim so typos are visible. `{language}`, `{codec_name}` and `{track_name}` come from the file's metadata and are sanitised for filesystem-unsafe characters before substitution, as is an attachment's extension that is not a known one. `build_output_file_name` adds the extension of the row's codec (`get_track_extension`), `join_output_path` joins it to the output directory, both normalised without touching the disk (a template's subfolders are kept, but its `..`, a leading `/` or a drive never leave the output directory, where 0.3.0 let `..` climb out; a relative directory keeps its leading `..`), and `build_extract_args` gives `tracks <id>:<path>… chapters <path> attachments <id>:<path>…`. `build_command_string` is the copyable command, quoted for the platform's shell (POSIX single quotes; the Command Prompt and `CommandLineToArgvW` rules on Windows, where a `%` goes outside the quotes behind a caret so `%NAME%` never expands, and the snackbar says the command is for the Command Prompt) with the `mkvextract` an extraction runs; it does not carry `--gui-mode`.

The active profile is consumed both on track auto-select (`state/files/load.rs`, `extract_args::TrackSelector`) and at extract time (`ExtractRequest`).

### Config file location

Config is stored per-OS:
- Windows — `%APPDATA%\BatchMkvExtract\` in installed mode (exe under `%LOCALAPPDATA%` / `%ProgramFiles%` / `%ProgramFiles(x86)%` / `%ProgramW6432%`), next to the `.exe` in portable mode.
- Linux — `$XDG_CONFIG_HOME/BatchMkvExtract/`, else `$HOME/.config/BatchMkvExtract/`.
- macOS — `~/Library/Application Support/BatchMkvExtract/`.

Detection lives in `crates/bme-core/src/config.rs::config_dir`. Old config files from earlier schema versions still load because every new field has a serde default; the only field 1.0.0 added is `window.display`. A file that cannot be read never stops the app: every value that can still be read is kept, the rest goes back to its default, the original is kept as `BatchMkvExtract.json.bad` (or `.2.bad` and so on, so no backup is ever replaced), and a notice says so at startup. Saves write a temporary file of their own and rename it over the old one. Another instance of the app may have saved since, so a save (`config::set_config` → `save_merged`) reads the file again under an interprocess lock (`BatchMkvExtract.json.lock`, `File::lock`) and applies only the values this instance changed since its last save or its load (objects member by member, anything else such as the profile list whole); a value changed in both is the later save's. The external tool paths live under `config.integration` (`mkvToolNixPath`, `betterMediaInfoPath`).

### i18n

Nine locales (`de`, `en-US`, `es`, `fr`, `it`, `ja`, `zh-CN`, `zh-HK`, `zh-TW`) in `crates/bme-app/locales/*.json` (rust-i18n, nested keys, `%{name}` placeholders; `settings.templatePlaceholdersHint` keeps literal single braces). When adding a user-facing string, add the key to **all nine** files: the test `i18n::tests::every_locale_has_the_same_keys_and_placeholders_as_en_us` fails otherwise, and `every_literal_key_in_the_sources_exists_in_en_us` scans `src/` for `tr!` / `rust_i18n::t!` keys. A missing key would fall back to `en-US`, but that's not a design pattern to lean on. Keys built at run time (theme names, queue statuses) are checked by their own tests. gpui-kit's own strings the app can show are in the `gpui_component` part of every locale file and layered over gpui-kit's with `i18n::install_component_strings` (rust-i18n accepts one extension per process, so it is once-guarded; tests may call it); keep that part's key set equal in all nine files, like every other key. The rust-i18n locale is process-wide (see the test notes below).

### External tools

Two optional external binaries are integrated, both opt-in via Settings:

- **MKVToolNix** (`mkvmerge` for the track listing, `mkvextract` for the extraction) — required for the core flow; the app shells out to them, and a path counts as found only when it has both.
- **BetterMediaInfo** — optional; when it is found, the "Open in BetterMediaInfo" entry becomes available on each card.

The core's detection (`mkvtoolnix::detect_mkvtoolnix`, `services::detect_better_media_info`) returns `MkvToolNixStatus` / `BetterMediaInfoStatus` (`crates/bme-core/src/protocol.rs`) with auto-detected directories and never writes the config; neither does an extraction that finds MKVToolNix by itself (on macOS, the newest `MKVToolNix-<version>.app` when the default path has no `mkvextract`): it reports the directory to the sink installed with `mkvtoolnix::init_auto_detected`, and the app stores it through `ConfigStore` (`tools::store_auto_detected`), so the Integration row shows it. Detect looks at a running `mkvtoolnix-gui` / BetterMediaInfo first, then the configured path (MKVToolNix: default `C:\Program Files\MKVToolNix`, `/Applications/MKVToolNix.app/Contents/MacOS`, `/usr/bin`); BetterMediaInfo also tries `%LOCALAPPDATA%\Programs`, `%ProgramFiles%` and `%ProgramFiles(x86)%`, `/Applications`, `/usr/bin` and `/usr/local/bin` (`crates/bme-core/src/services.rs`, `mkvtoolnix.rs`). There is no registry or `$PATH` search. One `ToolPathRow` (`ui/settings/integration.rs`) drives the Browse/Detect UI for both tools, so a change there updates both settings rows.

## GPUI and gpui-kit notes

### Versions and assets

- `gpui-kit` is an exact pin (`=0.10.0`). Its `test-support` feature is a dev-dependency only, so it never reaches the shipped binary. Because Cargo resolves weak `dep?/feature` entries into the lockfile, `test-support` makes `Cargo.lock` carry the `gpui-fast*` crates and their exact pins; they are never compiled. If a resolution conflict appears after a gpui-kit bump, re-resolve the gpui graph in one go instead of downgrading crates one by one. After a bump, also re-derive the Linux package dependencies (`docs/development.md`).
- Icons: `gpui_kit::assets::IconName` is the full Lucide catalog; `gpui_kit::component::IconName` is a small legacy subset. Only 106 SVGs are embedded by default; `src/assets.rs` adds the others the UI uses through `icon_assets!` and serves the app's own images (`images/icon.png`, the sibling apps' logos). A missing icon draws nothing and only logs `could not find asset`, so `assets::every_icon_the_sources_name_is_bundled` checks every `IconName::` the sources name. `build.rs` wraps the toolbar and card PNGs (`assets/{toolbar,cards}/*-256x256.png`) as SVGs, so GPUI tints them with the theme colour; only their alpha channel counts.
- `KeyBinding::new` cannot parse `secondary-…` (it needs the OS); bind `cmd-…` / `ctrl-…` per platform.

### Layout and rendering

- An `absolute()` element needs explicit insets (`top_0().left_0()`); without them taffy places it at its static position after its siblings.
- Cached views: the file list draws each card, and the queue each row, with `Entity::cached` at the height it measured in its last render (`CardHeight` reads the outer bounds during prepaint and requests a frame when the height changes), so a progress event or tick re-renders only that card. A cached view is laid out from the given style, never measured from its content, and it re-renders only when it or a descendant view is notified, when the window refreshes, or when its bounds move: a card growing a progress row moves the cards below it, which then render once. Reading a store during render does not invalidate a cached view; cards subscribe to the events of their own files. Every interactive element still works inside a cached view (hover and tooltips notify the view).
- GPUI does not replay a reused cached view's accessibility nodes, so a cached card or queue row drops out of the accessibility tree on every frame that reuses it: both lists draw through `CardHeight::view(view, cache)` with `cache = !window.is_a11y_active()`, uncached while a screen reader or other assistive client is connected. The test platform cannot turn accessibility on, but gpui-kit's test snapshots record each element's whole id path and the node properties GPUI gives AccessKit (a node id is the hash of that path, which holds every view and element id above it), so `ui::cards::tests::the_same_control_of_two_cards_is_two_accessibility_nodes` checks that the same control of two cards is two nodes with their own state and bounds. GPUI's fallback for an accessibility Click without a listener of its own clicks the centre of the node's bounds, which hits nothing for a card scrolled out of view. Open question: a live System Events check reported a later card's repeated controls with the first card's values; the tree GPUI builds does not, and it was not checked again with a native assistive client.
- `ButtonCustomVariant` paints its colour at 20 % strength in gpui-kit 0.10.0; a solid button adds `.bg(...)`. A disabled gpui-kit button keeps an icon colour set with `Icon::text_color`, so a coloured icon is applied only while the button is enabled.
- gpui-kit's scrollbar paints its 16 px track over the right edge of a scrolled view until it fades out; that overlap is not a layout fault. gpui-kit's `Scrollable` installs its own scroll handle; add a scrollbar to a tracked handle with `ScrollableElement::vertical_scrollbar(&handle)` instead. A scroll container without `restrict_scroll_to_axis()` turns a wheel delta of the other axis into its own (a vertical wheel over a sideways-scrolling table slides it).
- `Checkbox::indeterminate(bool)` (gpui-kit 0.10.0) draws the track table's mixed select-all state; accesskit reports it as `true` on macOS.
- GPUI draws colour emoji on Linux only from the font named `NotoColorEmoji`, which is why the Linux packages require Noto Color Emoji.

### Input, keys and dialogs

- A key binding beats an element's key-down listeners and text input, so a plain `space` binding would steal Space from focused buttons and from text fields; a keystroke interceptor (`cx.intercept_keystrokes`) sees the context stack and the window first and consumes only what it handles.
- An action dispatched by a key press runs while its window is being updated, so a global handler cannot `update` that window: defer with `cx.defer` (the Quit handler does).
- GPUI does not draw before dispatching a mouse event, so listeners registered in a paint (`window.on_mouse_event`) miss a release that comes before the next frame; the group card's splitter also listens with `on_mouse_up_out`.
- `InputState::set_value` emits no `Change`. The profile editor fills a field in from the store only when the profile's value changed since it last filled it in, so a field's own typing is never put back while its writes are pending.
- A gpui-kit dialog binds Enter to its Confirm action, which closes it without calling a form's own handler: route `Dialog::on_ok` to the form and return `false` until the form closes the dialog itself.

### Tests

- UI tests use `#[gpui_kit::test]` and `gpui_kit::test::TestWindowExt` (`click`, `drag`, `input`, `press`, `find`). Mark elements a test must find with `.test_support()` (`gpui_kit::base::TestSupportExt`; a no-op without the feature). In a test module that sees `gpui_kit::*`, add `use core::prelude::v1::test;`, because the glob also exports GPUI's `test` macro and `#[test]` would recurse.
- GPUI delivers focus events only to an active window and through deferred effects: call `window.activate_window()` once and `cx.run_until_parked()` after a click before typing.
- Test queries see only elements marked `.test_support()` and gpui-kit's own components; icon-only buttons need `.accessibility_label(...)` (the tooltip text) to be found by label, which also names them for screen readers. Text components record their text for tests (`gpui_kit::base::TestTextExt::test_text`, read back with `gpui_kit::base::test_support::texts(window)`); the cards mark their texts so tests can read what is shown. `.test_support()` wraps the element type under the test feature, so a helper returns `AnyElement`.
- gpui-kit findings: `RadioGroup` renames its radios by index (find them by label); a `Select`'s options and a `ButtonGroup` itself are not test-visible (drive the select by keyboard); the settings sidebar entries are `0-<page>`.
- `TestWindowExt::render_frame` refreshes the window and so bypasses caching; a test that counts renders draws with `window.draw(cx).clear(cx)`.
- The rust-i18n locale is process-wide: a test that renders the shell or switches the language holds `i18n::tests::LOCALE_LOCK` (the shell test helper does), or text width changes under another test's click. `Config::default()` detects the system language; tests set `language` explicitly.
- GPUI's test scheduler panics when another thread wakes a foreground task: a test that runs the core's extract queue relays the worker events through the test thread.
- Tests read system notifications with `TestAppContext::shown_system_notifications()`, which records only after `cx.set_app_identity(...)`.
- The test platform answers a path prompt only with paths or a cancel (`simulate_path_prompt_response`), never an error: a picker's failure is tested through the handler it goes to (`platform::dialogs::take_chosen`, `ToolPathRow::dialog_failed`).
- gpui-kit binds Tab in its `Root` key context, which is on the dispatch path only once an element has the focus: a test that tabs starts with `Window::focus_next`. A snapshot's `focused()` needs `.test_support()` before `.track_focus(...)`.
- Tests that press editing shortcuts use the platform's key (Select All is Cmd+A on macOS, Ctrl+A elsewhere), and tests that compare checked-in text files normalise line endings (Windows checks them out with CRLF).

### Live checks on macOS

- Run the release app with a scratch `HOME`; the config directory follows `$HOME`, so the real config stays untouched.
- System Events can drive the app through its accessibility tree: buttons by their title, `enabled`, table rows, checkboxes and text fields with their values. Read the tree only after the views were drawn uncached (an assistive client turns caching off; before that, a 1 px window resize redraws everything). Plain text (status labels, toasts, the topmost window's lines) has no accessibility role, and the Settings dialog's sidebar entries are not in the tree: typing a page's term into the dialog's Search reaches its page. A later card's repeated controls were seen reporting the first card's values there (System Events addresses an element by its name or index, which finds the first match), so drive the card under test as the first card and keep it scrolled into view.
- System Events' `click at` is an accessibility press, which does not focus a GPUI input; `set focused of text field N of group 1 of window 1 to true` does. A field's accessibility `value` follows the text about a frame late, so wait about a second before reading it. Clicks posted to the app's process (`CGEvent.postToPid`) do not arrive.
- A named pipe (`mkfifo`) at one of a file's output paths holds `mkvextract` at 98 % until it is killed, which makes cancel and close-guard checks reliable. A Lucide icon missing from the bundle shows only in the log, so read it after a live run. `screencapture` needs screen-recording permission.

## Packaging and CI

- Packaging metadata is in `crates/bme-app/Cargo.toml` (`[package.metadata.packager]`, `[package.metadata.generate-rpm]`) and `crates/bme-app/packaging/` (icons, desktop file, the macOS `Info.plist` overlay, the WiX template). Every installer identity matches the 0.3.0 release: deb and rpm package `batch-mkv-extract`, bundle id `com.caoccao.batch-mkvextract`, NSIS per-user install with publisher `caoccao`, and the MSI UpgradeCode `{25D36AF1-44A1-5CDA-8EDB-88642216E69F}`, which `packaging/wix/main.wxs` pins because cargo-packager would derive a different one. `packaging/macos/Info.plist` is merged over the generated `Info.plist` and sets `CFBundleVersion` to the version, as 0.3.0 had, instead of cargo-packager's build timestamp. There is no `license-file`: cargo-packager would turn it into a license agreement before the `.dmg` opens and a license page in the NSIS and MSI installers, which 0.3.0 did not have. cargo-packager rejects unknown keys (NSIS takes `installMode`, not `install-mode`). One desktop id everywhere: `BatchMkvExtract` is the desktop file's basename, the Wayland app id, `StartupWMClass` and the launcher-progress URI.
- Linux dependencies: the `.deb` `depends` are `dpkg-shlibdeps`'s list for the `ubuntu-22.04` `dist` binary plus what GPUI loads at run time (Vulkan loader, Wayland client, EGL and wayland-egl for wgpu's GL fallback, `fontconfig-config` for `/etc/fonts/fonts.conf`, which a pure-Rust parser reads, and Noto Color Emoji); the `.rpm` gets the linked libraries from rpm's own soname scan and lists the rest as capabilities (`libvulkan.so.1()(64bit)`, `font(notocoloremoji)`, …). Re-derive both after a gpui-kit bump (`docs/development.md`). File dialogs need an XDG desktop portal, which desktops provide; it is not a dependency.
- CI: three workflows, `linux_build.yml` (`ubuntu-22.04` for a low glibc floor; GPUI's build dependencies and Mesa's Vulkan drivers, the headless UI tests, the coverage gate, `.deb`, `.AppImage`, `.rpm`), `macos_build.yml` (`.dmg` for x86_64 on `macos-15-intel` and arm64 on `macos-15`) and `windows_build.yml` (one `.msi` per language and the NSIS `.exe`). Each runs `cargo test --release --workspace --locked` (Linux leaves `bme-core` out there, as the coverage gate runs its tests), builds with `--profile dist` and uploads seven artifacts in all, named `BatchMkvExtract-<os>-<arch>-<version>`, with `-<format>` on Linux and Windows (the names of the 0.3.0 artifacts). Installers are unsigned (an ad-hoc signature on macOS). The workflows run with `permissions: contents: read` and pin every action to a commit SHA (tag in a comment; `.github/dependabot.yml` proposes updates); Linux has a non-blocking `lint` job (`cargo fmt --all --check`, `cargo clippy --release -p bme-core --all-targets`).

## Project conventions
